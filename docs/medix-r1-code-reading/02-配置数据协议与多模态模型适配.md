## 1. 本篇的四层心智模型

```text
实验配置层：PPOConfig / WorkerConfig / Shell overrides
数据语义层：problem / solution / image / Prompt 模板
批数据协议层：DataProto.batch / non_tensor_batch / meta_info
模型适配层：Qwen mRoPE / padding-free / FlashAttention / Ulysses
```

很多训练问题看起来发生在 GPU，实际根因可能在更早的位置。例如 Reward 全为 0 可能是 `ground_truth` 格式不满足 `medical.py` 的假设；图像 token 与视觉特征数量不一致可能来自 Prompt 占位符或图像列表；Policy Loss shape 错误可能来自 `DataProto.repeat()` 后某个非 Tensor 字段没有同步扩展。

## 2. 配置文件与 Python dataclass 的职责边界

配置来源有三层：

| 来源 | 文件/对象 | 作用 |
|---|---|---|
| Python 默认值 | `verl/trainer/config.py`、`verl/workers/**/config.py` | 定义完整字段集合、默认行为和派生字段 |
| 基础实验配置 | `training/examples/config.yaml` | 提供一套可读的 GRPO/PPO 基线值 |
| 医学实验覆盖 | `medix-r1_2b_dapo.sh`、`medix-r1_8b_gspo.sh` | 替换数据、模型、Reward、长度、batch、算法和资源 |

不要把 `config.yaml` 理解成独立真相。它仍然写着 math12k、Qwen2.5-7B、数学 Prompt 和数学 Reward；医学 Shell 脚本依靠 CLI override 把这些字段改成医学配置。

## 3. `PPOConfig`：顶层配置树

`PPOConfig` 只有四个一级字段：

```python
@dataclass
class PPOConfig:
    data: DataConfig
    worker: WorkerConfig
    algorithm: AlgorithmConfig
    trainer: TrainerConfig
```

它们分别回答：

| 一级配置 | 核心问题 |
|---|---|
| `data` | 数据从哪里来、字段叫什么、最长多少、怎样格式化 |
| `worker` | Actor/Ref/Critic/Rollout/Reward 怎样构造和分布式运行 |
| `algorithm` | Advantage、KL 和 online filtering 用什么策略 |
| `trainer` | 训练多久、用多少 GPU、何时验证/保存、写什么日志 |

### 3.1 `recursive_post_init()`

`deep_post_init()` 不是只调用顶层一次，而是递归遍历所有 dataclass 字段。处理顺序是先调用当前对象的 `post_init()`，再进入子对象。对 `PPOConfig` 来说，先把长度和 KL 配置传播给 Worker，然后再由子配置做路径解析和校验。

这种顺序目前可工作，但阅读时要注意：一个子对象的 `post_init()` 可能依赖父对象刚写入的派生字段。

## 4. `DataConfig`：输入契约

`DataConfig` 的字段可分为四组：

| 组 | 字段 | 说明 |
|---|---|---|
| 数据定位 | `train_files`,`val_files` | HF ID、本地目录或 Parquet；支持 `@split` |
| 字段映射 | `prompt_key`,`answer_key`,`image_key`,`video_key` | 把任意 Dataset 列统一成训练语义 |
| 序列限制 | `max_prompt_length`,`max_response_length` | 分别限制输入和生成长度 |
| 媒体处理 | `image_dir`,`video_fps`,`min_pixels`,`max_pixels` | 图像路径前缀、视频抽帧和缩放限制 |
| DataLoader | `rollout_batch_size`,`mini_rollout_batch_size`,`val_batch_size`,`shuffle`,`seed` | prompt batch 与迭代方式 |
| Prompt | `format_prompt`,`override_chat_template` | Jinja 模板和 tokenizer/processor Chat Template |

### 4.1 医学脚本的实际字段映射

基础 YAML 是：

```text
prompt_key=problem
answer_key=answer
image_key=images
```

其中 `prompt_key=problem` 已经是医学数据使用的字段，但两个医学脚本仍显式覆盖 `answer_key=solution` 与 `image_key=image`。所以预期样本至少需要：

```python
{
    "problem": "医学问题",
    "solution": "包含模态前缀的标准答案",
    "image": [image_or_path, ...],
}
```

README 把 `image` 描述为 `Sequence[Image]`。如果实际数据是一张裸 `PIL.Image` 而不是列表，`__getitem__()` 中的 `len(images)` 和 `for image in images` 就会采用不同语义，因此必须先用真实样本验证字段类型。

## 5. `medical_format.jinja`：训练输出协议的起点

医学模板要求模型输出三部分：

```text
<医学模态标签>
<thinking>医学推理</thinking>
<answer>最终答案</answer>
```

模态标签限定为 X-ray、CT、MRI、OCT、PET、超声、病理显微等 16 类。模板最后是：

```text
Question:
<image>{{ content | trim }}
```

其中 `<image>` 不是最终直接送入模型的普通文本。`RLHFDataset._build_messages()` 会把它转换成结构化 `{"type":"image"}` 项目。

### 5.1 Prompt 与 Reward 不是完全同一个契约

Prompt 要求先输出模态，再输出 `<thinking>` 与 `<answer>`；但 `format_reward()` 从第一个 `<thinking>` 开始做 full match，所以它只验证后两段，不验证前面的模态标签。模态由独立 `modality_reward()` 负责。

另一个关键点是标准答案。`medical.py` 用 `ground_truth.split(">", maxsplit=1)` 分离模态和答案，因此标准答案预期类似：

```text
<X_RAY> pneumonia
```

如果 `solution` 只是 `pneumonia`，没有 `>`，两个 accuracy reward 会因异常返回 0，modality reward 的提取也会失去正确契约。训练数据 schema 必须包含这一事实，而不能只写“solution 是答案字符串”。

## 6. `RLHFDataset.__init__()`：四种数据加载路径

### 6.1 `@split` 解析

当路径包含 `@` 时，代码使用 `data_path.split("@")` 得到路径和 split；否则 split 默认为 `train`。当前实现没有限制只切一次，因此路径本身若意外包含多个 `@` 会解包失败。常规 Hugging Face ID 和本地路径通常不会遇到这个问题。

### 6.2 本地目录

如果 `data_path` 是目录：

1. 优先寻找文件名以 split 开头且扩展名为 `.parquet` 的文件；
2. 若没有，再使用目录下全部 Parquet；
3. 若仍没有，调用 `load_from_disk(data_path)[split]`。

这允许同一个目录同时容纳 `train-*.parquet` 和 `test-*.parquet`。

### 6.3 单文件

如果是文件，固定按 Parquet 加载并使用 `split="train"`。因此本地 JSON/JSONL 文件不能直接放进 `data_path`，除非先转换或扩展代码。

### 6.4 Hugging Face Dataset

其他情况直接调用：

```python
load_dataset(data_path, split=data_split)
```

8B 脚本使用的 `MBZUAI/medix-rl-data@train` 会走这一分支。

## 7. 过长 Prompt 的预过滤

`filter_overlong_prompts=True` 时，Dataset 在初始化阶段执行 Hugging Face `dataset.filter()`，默认 `num_proc=16`。每条样本会：

```text
构造 messages
→ 选择 processor 或 tokenizer
→ apply_chat_template(add_generation_prompt=True)
→ 比较长度是否 ≤ max_prompt_length
```

这一步发生在 DataLoader 之前，可以避免训练中频繁因超长样本抛错，但有三个代价：首次启动耗时、并行进程内 tokenizer/processor 的可序列化要求，以及“模板变化后缓存是否失效”的 Hugging Face Dataset 行为需要关注。

`__getitem__()` 后面仍有截断逻辑。医学 DataLoader 把 `truncation="right"` 传给 Dataset，因此预过滤和最终截断构成双重保护；如果关闭预过滤，过长 prompt 会在右侧截断，而不是报错。

## 8. `_build_messages()`：文本、图像和视频三条分支

### 8.1 图像分支

只要 `image_key` 存在于样本字典，就走图像分支。代码按 `<image>` 切分 Prompt，每遇到一个分隔符插入一个 image item。

例如：

```text
前置说明<image>问题正文
```

转换为：

```python
[
    {"type": "text", "text": "前置说明"},
    {"type": "image"},
    {"type": "text", "text": "问题正文"},
]
```

占位符个数与 `example[image_key]` 中图像数量必须匹配，真正的 processor/model forward 会校验视觉 token 和视觉特征数量。

### 8.2 视频分支

只有样本不存在 image key、但存在 video key 时才进入。它用 `<video>` 占位符构造消息。由于 image 分支优先，一个同时包含 `image` 和 `videos` 字段的 Dataset 会忽略视频分支。

### 8.3 文本分支

没有图像和视频字段时，content 直接是字符串，使用 tokenizer 而不是 processor 编码。这使同一个 Dataset 类能训练纯文本任务和 VLM 任务。

## 9. `process_image()`：像素限制不是固定宽高

图像处理按总像素数缩放：

- 若 $W\times H>max\_pixels$，按比例缩小；
- 若 $W\times H<min\_pixels$，按比例放大；
- 最后转换为 RGB。

缩放因子为 $\sqrt{target/(W\times H)}$，所以保持宽高比。默认 `min_pixels=262144`、`max_pixels=4194304`，即大约从 $512^2$ 到 $2048^2$ 的总像素范围，但非正方形图像不会被强制变成正方形。

图像在 Dataset 编码时处理一次，随后 `multi_modal_data` 保存的仍是原始 `images`，在 vLLM rollout 和 FSDP forward 前还会再次调用 `process_image()`。这是为了分别满足 processor tokenization、vLLM 输入和 PyTorch forward，但会增加 I/O 与解码成本。

## 10. `__getitem__()`：图像样本的完整转换

图像分支依次执行：

```text
processor.apply_chat_template(..., tokenize=False)
→ 解析相对 image_dir
→ process_image()
→ processor(images, text)
→ 取 input_ids / attention_mask
→ 保存原始 multi_modal_data
→ 计算 position_ids
→ 左填充/右截断到 max_prompt_length
→ 保存 raw_prompt_ids
→ answer_key 改名为 ground_truth
```

注意 `multi_modal_data={"images": images}` 保存的是处理前的 `images` 变量，而传给 processor 的是 `processed_images`。如果原始对象是文件路径，后续 Worker 可以重新按自己的像素配置打开；如果原始是 PIL 对象，则会再次加载/转换。

### 10.1 空图像列表

如果 image 字段存在但列表为空，`processed_images=None`，这条数据仍走 processor 的 VLM 分支，可以形成 text-only 样本。是否被具体 Qwen Processor 接受，需要在对应 Transformers 版本中验证。

## 11. Qwen-VL 的 `position_ids` 为什么是四通道

普通文本位置是一个一维序列；Qwen-VL 的视觉 token 使用多维 rotary position。Dataset 对 Qwen2-VL/Qwen3-VL 生成三维视觉位置，再额外拼接普通文本位置：

```text
position_ids shape = (4, sequence_length)
第 0 行：统一文本序号
第 1~3 行：时间、高度、宽度方向的视觉位置
```

DataLoader stack 后变成 `(batch,4,seq)`；Actor forward 前又转置为模型期待的 `(4,batch,seq)`。

### 11.1 `get_rope_index()` 的职责

Qwen3-VL 版本会：

1. 找出 vision start token 后是 image 还是 video；
2. 根据 `image_grid_thw`/`video_grid_thw` 获取视觉网格；
3. 用 `merge_size` 将原始网格换算成 LLM token 网格；
4. 为文本段生成连续位置；
5. 为视觉段生成 T/H/W 位置；
6. 把所有段拼成三行视觉 position IDs。

这个位置必须在 sequence sharding 前计算，否则每个 Ulysses rank 只看到局部 token，无法恢复完整图文布局。

## 12. `postprocess_data()`：左填充 Prompt

`torch_functional.postprocess_data()` 负责把 `input_ids`、`attention_mask` 和 `position_ids` 调整为固定 `max_prompt_length`。训练代码采用左填充，因为生成时通常希望有效 prompt 紧贴 response 左侧；response 在 vLLM 生成后则右填充。

典型布局：

```text
input_ids:      [PAD PAD prompt tokens | response tokens PAD PAD]
attention_mask: [  0   0      1 ... 1 |      1 ... 1   0   0]
```

`raw_prompt_ids` 不包含 padding，它直接提供给 vLLM，避免 vLLM 需要理解训练侧的固定长度布局。

## 13. DataLoader：为什么训练使用 `StatefulDataLoader`

训练集使用固定 seed 的 `RandomSampler` 而不是 `shuffle=True`，并将其交给 `StatefulDataLoader`。保存 checkpoint 时 `RayPPOTrainer` 会额外保存 `train_dataloader.state_dict()`；恢复时加载这个状态。

目标是同时恢复：

```text
当前 epoch/iterator 位置
Sampler 的随机顺序
下一批将读取哪些样本
```

但是精确复现还取决于 Dataset filter/cache、多个 DataLoader worker、随机图像处理、Ray Worker RNG 和 vLLM RNG。代码也会保存 CPU/CUDA/NumPy/Python RNG 状态，说明作者试图构建较完整的恢复链路。

## 14. `collate_fn()`：Tensor 与对象为什么必须分开

Dataset 样本中既有可 stack 的 Tensor，也有字符串、list、PIL/path 等对象。`collate_fn()` 将它们分为：

```text
Tensor → torch.stack(..., dim=0)
其他值 → np.array(..., dtype=object)
```

这直接对应 `DataProto` 的两套容器。把图像元数据强行塞进 TensorDict 不现实，把 input IDs 留在 object array 又会失去高效的 device move、split 和 concat。

## 15. `DataProto` 的三个区域

### 15.1 `batch`

类型是 `TensorDict`，要求所有 Tensor 在前 `num_batch_dims` 上具有相同 batch size。常见 key：

```text
input_ids, attention_mask, position_ids
prompts, responses, response_mask
old_log_probs, ref_log_probs, values
token_level_scores, token_level_rewards
advantages, returns
```

### 15.2 `non_tensor_batch`

值必须是 `dtype=object` 的 NumPy array。常见 key：

```text
ground_truth
raw_prompt_ids
multi_modal_data
multi_modal_inputs
uid
训练/Actor 返回的 metrics
```

### 15.3 `meta_info`

不按样本逐条存储，而是整个 DataProto 共享，例如：

```text
temperature, n, eos_token_id
min_pixels, max_pixels, video_fps
global_token_num
```

`meta_info` 在 `chunk()`、`repeat()` 等操作中通常直接共享同一个字典引用或复用内容，所以不应把逐样本可变数据放进去。

## 16. DataProto 关键方法速查

| 方法 | 是否修改原对象 | 主要用途 |
|---|---:|---|
| `from_single_dict()` | 新建 | 自动区分 Tensor 与非 Tensor 字段 |
| `from_dict()` | 新建 | 显式构造 TensorDict/object array/meta |
| `select()` | 新建视图式对象 | 只选择某些字段，不从原对象删除 |
| `pop()` | 是 | 从主 batch 取走一组字段，生成子 DataProto |
| `union()` | 是 | 合并两个协议对象并检查冲突 |
| `repeat()` | 新建 | 将 prompt 侧数据重复 `n` 次以对齐 rollout |
| `reorder()` | 是 | 按长度均衡后的索引重排 Tensor 与非 Tensor |
| `chunk()` | 新建列表 | 按 Worker 数平均切分 |
| `split()` | 新建列表 | 按固定每块大小切分 |
| `concat()` | 新建 | 累积 online filtering 保留的多批样本 |
| `to()` | 是 | 只移动 TensorDict 到目标设备 |
| `save_to_disk()`/`load_from_disk()` | 持久化 | 保存协议对象，当前训练主链主要用专用 checkpoint |

### 16.1 `union()` 是数据契约检查点

`union_tensor_dict()` 和 `union_numpy_dict()` 会检查重复 key 是否相等；`meta_info` 也通过字典 union 检查冲突。这可以防止把不同 batch 的同名字段静默覆盖。

### 16.2 `repeat(interleave=True)`

对 prompt 顺序 `[A,B]`、`n=3`，interleave 结果是：

```text
[A,A,A,B,B,B]
```

这与 vLLM `completion.outputs` 的展开顺序一致，也是 GRPO 按连续 uid 分组的自然布局。若改成非 interleave，则会变成 `[A,B,A,B,A,B]`。

## 17. `DataProtoFuture`：设计中的异步数据通道

`DataProtoFuture` 保存 Ray `ObjectRef`、collect function 和可选 dispatch function，目的是让一个 WorkerGroup 的输出不必立刻拉回 Driver，再发送到另一个 WorkerGroup。

Base decorator 中支持：

```text
DataProtoFuture.chunk()
DataProtoFuture.get()
_materialize_futures()
```

不过当前 Ray Controller 具体实现缺失，因此本地无法验证哪些调用真正保持 future、哪些调用会提前 materialize。只能确认 Base 层为异步传递预留了协议。

## 18. Worker 方法的 dispatch 元数据

`@register(...)` 不会直接执行 Ray RPC，只是在函数对象上添加：

```python
{
    "dispatch_mode": ...,
    "execute_mode": ...,
    "blocking": ...,
}
```

`WorkerGroup._bind_worker_method()` 读取这些属性，为 WorkerGroup 动态生成同名方法。

### 18.1 主要 Dispatch 模式

| 模式 | 输入分发 | 输出收集 | 使用场景 |
|---|---|---|---|
| `ONE_TO_ALL` | 同一参数发给全部 Worker | 原样列表 | 初始化、保存、切换 rollout 引擎 |
| `ALL_TO_ALL` | 调用方已经给每个 Worker 准备参数 | 原样列表 | 通用逐 rank 调用 |
| `DP_COMPUTE_PROTO` | DataProto 按 world size 平均 chunk | concat 为一个 DataProto | 生成、log-prob、Actor/Critic 更新 |
| `DP_COMPUTE_PROTO_WITH_FUNC` | 第一个参数是函数，其余 DataProto 切分 | concat | 在 Worker 上执行自定义函数 |
| `DP_COMPUTE_METRIC` | DataProto 切分 | 保留每 rank 结果列表 | 指标类任务 |

当前 `FSDPWorker.generate_sequences()`、`compute_log_probs()`、`update_actor()` 都用 `DP_COMPUTE_PROTO`。因此 Driver 看见的是一个逻辑 batch，WorkerGroup 负责按 rank 切分与重组。

## 19. `_balance_batch()` 与 Dynamic Batching 是两层不同优化

### 19.1 Driver 全局长度均衡

`RayPPOTrainer._balance_batch()` 根据每条完整 sequence 的有效 token 数，把样本重新排序，使每个 Data Parallel rank 分到的总 token 更接近。它解决“某个 rank 分到的长样本过多，其他 rank 等待”的问题。

### 19.2 Worker 内动态 micro-batching

Actor 内部的 `prepare_dynamic_batch()` 根据 token budget 把本 rank 数据重新组合成长度总量接近的 micro-batch。它解决单 rank 内固定样本数 micro-batch 因长度差异造成显存浪费的问题。

两者都可能改变样本顺序，因此代码必须用 index map 在输出后恢复顺序。GRPO 的分组依据不是物理相邻位置，而是 `uid`，所以在全局重排后仍能找回同一 prompt 的 response。

## 20. Padding-free forward

`DataParallelPPOActor._forward_micro_batch()` 在 `padding_free=True` 时：

```text
unpad_input 去掉所有 padding token
→ 把 batch 拼成一条 packed token 流
→ 同步 unpad position_ids
→ 必要时按 Ulysses 切 sequence
→ 模型 forward，无 attention_mask
→ 直接计算下一个 token 的 log-prob
→ gather Ulysses 输出
→ pad_input 恢复 batch×sequence
→ 只截取 response 区间
```

这样可以避免对大量 padding 进行 Attention 计算，但要求 FlashAttention 能理解变长序列边界和多维 position IDs。

## 21. `apply_ulysses_patch()`：为什么要 Monkey Patch Transformers

padding-free 模式下，项目会全局修改：

```text
ALL_ATTENTION_FUNCTIONS["flash_attention_2"]
Qwen2/2.5-VL Model.forward
Qwen3-VL / Qwen3-VL-MoE Model.forward
对应 ConditionalGeneration.forward
```

支持的模型类型包括 Llama、Gemma、Mistral、Qwen2/3、Qwen MoE 和 Qwen-VL。Transformers 版本低于 4.54.0 会直接报错。

这个 patch 的目标有两个：让 FlashAttention 兼容 packed/sequence-parallel 输入，以及让 Qwen-VL 在图文混合、padding-free、mRoPE 场景正确构造 embedding 和 forward。

## 22. Qwen3-VL forward patch

### 22.1 `_get_input_embeds()`

它先获取文本 token embedding，再处理图像/视频：

1. 调视觉塔得到 image/video embedding；
2. 统计输入中的视觉 token 数；
3. 校验视觉 token 数等于视觉 feature 数；
4. 用 `masked_scatter` 把视觉 embedding 写入 token embedding；
5. 准备 deepstack visual embedding；
6. 对纯文本样本构造 dummy vision forward，并以 `0.0 * mean` 接入计算图。

最后一项看似多余，实际可让图文混合 batch 或分布式参数使用保持一致，避免某些视觉参数在纯文本样本上完全不参与图。

### 22.2 `qwen3_vl_base_forward()`

它要求位置张量为 `(4,batch,seq)`，调用 `_get_input_embeds()`，然后直接调用底层 `language_model(input_ids=None, inputs_embeds=...)`。

### 22.3 `qwen3_vl_model_forward()`

它调用 patched base model，取 hidden states，再经过 `lm_head` 得到 logits。这里不计算语言模型 loss，因为 RL Actor 自己根据 response token 的 log-prob 构造 Policy Loss。

## 23. FlashAttention patch 与 Ulysses

`flash_attention_forward()` 先把 Q/K/V 转成 FlashAttention 需要的布局，再进入 `_custom_flash_attention_forward()`。

当 Ulysses sequence parallel size 大于 1 时：

```text
每个 rank 持有 sequence 的一部分、全部 heads
→ all-to-all：聚合 sequence、切分 heads
→ 在本 rank 对完整 sequence 的部分 heads 做 Attention
→ all-to-all：聚合 heads、重新切分 sequence
```

对不单调 position IDs，代码用 `position_ids==0` 推导变长序列边界，调用 `flash_attn_varlen_func()`。这正是 packed sequence 和 Qwen-VL mRoPE 需要定制 attention 的原因。

### 23.1 当前实现中值得核查的一行

代码先创建 `position_ids_lst`，随后写：

```python
position_ids = dist.all_gather(position_ids_lst, position_ids, group=...)
position_ids = torch.cat(position_ids_lst, dim=-1)
```

PyTorch `dist.all_gather()` 通常原地填充列表且返回 `None`。这里第一行把 `position_ids` 赋成 `None`，第二行实际仍使用已填充的 `position_ids_lst`，所以结果能来自列表，但赋值本身没有意义，容易误导维护者。

## 24. 多模态数据为什么在三个地方处理

| 阶段 | 输入 | 处理目标 |
|---|---|---|
| Dataset | 原始图像/路径 | 让 processor 生成 prompt token、grid 和初始 position IDs |
| vLLM Rollout | `multi_modal_data` | 转成 vLLM 接受的 PIL 图像或视频帧 |
| FSDPWorker | `multi_modal_data` | 转成 PyTorch Actor forward 所需的 pixel values/grid tensors |

FSDPWorker 用 `uid` 做 cache：同一 prompt 的 `n` 条 response 共享同一份视觉预处理结果，避免重复处理图像。若新 batch 的 uid 变化，cache 清空。

## 26. 当前数据与协议层的风险清单

| 风险 | 触发条件 | 结果 |
|---|---|---|
| 2B 本地数据缺失 | 直接运行 2B 脚本 | Dataset 路径解析失败 |
| 标准答案无模态前缀 | `solution` 不含 `>` | accuracy/modality Reward 大量为 0 |
| Prompt 图像占位符与列表不一致 | `<image>` 数量不同 | processor/model 的视觉 token 校验失败 |
| image 和 video 字段同时存在 | Dataset schema 同时保留两列 | image 分支优先，video 被忽略 |
| DataProto batch 维度不一致 | 自定义模块只扩展 Tensor 或非 Tensor 一侧 | consistency/concat/index 失败或错位 |
| `meta_info` 放逐样本数据 | chunk/repeat 后仍共享 | rank 间或样本间语义错误 |
| Transformers 版本过低 | `<4.54.0` | Monkey patch 直接拒绝 |
| FlashAttention 未安装 | padding-free 代码使用 `unpad_input` 等 | import 被 `pass` 吞掉，运行到方法时才出现名称错误 |
| Ray Controller 缺失 | 进入训练 import | Base dispatch 设计存在，但远程执行链不可用 |

最后一项说明了一个重要边界：72 个 Python 文件都能通过 AST 解析，只证明语法正确，不证明相对 import、第三方依赖和 GPU runtime 可用。

## 27. 推荐的单样本调试顺序

在修复启动阻断、准备依赖后，最值得先做的不是直接多 GPU 训练，而是逐层打印 shape 和字段：

```text
原始 Dataset sample 的 key 与类型
→ _build_messages() 结果
→ processor chat template 文本
→ __getitem__() 返回 key、shape、ground_truth
→ collate_fn 两条样本
→ DataProto.from_single_dict()
→ pop/repeat/union 后 key 和 batch size
→ vLLM generate 后 response_mask
→ FSDPWorker multi_modal_inputs cache
→ Actor _forward_micro_batch() log_probs shape
```

每一层只验证一个契约，能够快速区分“数据字段问题”“多模态 processor 问题”“DataProto 对齐问题”和“分布式/GPU 问题”。

## 28. 阅读完成后的自检

你应该能够回答：为什么原始图像既进入 Dataset processor，又被保存在 `multi_modal_data`；为什么 Prompt 左填充而 response 右填充；为什么 Qwen3-VL position IDs 有 4 个通道；`DataProto.repeat(interleave=True)` 怎样保持 prompt 与 `n` 条 rollout 对齐；`uid` 同时服务于 GRPO 分组、online filtering 和多模态 cache；为什么 padding-free 训练需要 Monkey Patch FlashAttention；以及为什么缺少 `single_controller/ray` 时，Base decorator 再完整也无法启动实际 Ray Worker。
